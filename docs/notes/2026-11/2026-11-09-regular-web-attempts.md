## 一、起点

| 类别 | 总数 | 已解 | 解题率 |
|---|---|---|---|
| 有 CVE | 72 | 53 | **74%** |
| 常规题（无 CVE） | 58 | 17 | **29%** |

常规题从 21% 升到 29%（11-09 新增 2 道，都是常规题），仍是短板，34 道未解。

## 二、否掉的路：扩大技法语料

### 假设

`data/knowledge/injection.jsonl` 里有 10 条最精准的技法定义（error/union/time-based SQLi、OS command injection、Jinja2 SSTI、XXE、NoSQL operator、LDAP filter），但一条都没被用上。查下来有两个断点：

1. `technique_candidates` 只收 `kind == "technique"`，而这 10 条是 `kind: poc` —— 语料 1670 条里有 1476 条 poc 全被排除；
2. 就算读进来，语料名（`OS command injection`）和探针名（`Command injection and RCE`）对不上，也过不了白名单。

于是实现了 `_technique_class()` 别名表 + 关键词回落，把 poc 条目归一到 11 个探针类。

### 结果：无效

计数从 `Command injection 9` 变成 **398**，但——

```
Web9              -> [cmdi 398, SSTI 17, deser 89]
Web6              -> [cmdi 398, SSTI 17, deser 89]
Wallbreaker_Easy  -> [cmdi 398, SSTI 17, deser 89]
Online Tool       -> [cmdi 398, SSTI 17, deser 89]
```

**四道完全不同的题，候选列表一个字符都不差。**

根因：排名是按语料条目数排的。一个类一旦压倒性领先，扩大输入只会放大它，不会产生区分度。

**教训：计数不是信号。** 常规题缺的不是「每类更多条目」，而是「关于这个目标的任何观察」。全域频率先验给不了这个，所以扩大一个忽略输入的排名的输入，只是动作，不是进展。

**已全部回滚**（别名表保留，注释写明为何不接线）。

## 四、修法

新增 `stagnation_repeat_limit = 5`：按**命令前 60 字符指纹**检测连续重复。

关键设计决定：

1. **放在 `learned` 分支之前**。第一版写在后面，而 `learned` 分支会提前 `return` —— 于是它只在「看起来没产出」的命令上运行，恰好是不需要它的那些。测试（连发 5 条都带 `VERIFIED_FACT=`）当场证明它永不收敛。
2. **首见计入 1**。否则 `REPEAT:5` 要到第 6 条才触发，与名字不符。
3. **短命令豁免**。`<20` 字符返回 `None`，`ls`/`pwd` 反复不触发。
4. **只比前缀，不做相似度**。token 重叠或编辑距离会把「同一端点换参数」也算重复，而 `?id=1` / `?id=2` 正是有效探测的样子。要抓的是字节级重发的退化情形。

## 五、测试

新增 6 条：

- 同一命令 5 次触发
- 输出看起来像进展（带 `VERIFIED_FACT=`）也照触发
- 变化参数 10 次不触发
- 短命令 10 次不触发
- `repeat_limit=0` 可关闭
- A-B-A-B 交替不触发

回归 **2467 → 2473 passed**。

## 七、第一个真实证据（2026-11-09 21:48）

|---|---|---|---|---|

旧 Run 里能直接看到重复检测要抓的形态：

```
33x /bin/bash -c "cd /home/kali/workspace/shared/recon && python...

```

`33x` 那条正是连续重发，`REPEAT:5` 会在第 5 次时要求收敛。

### 但必须克制

样本 1 道。「1086 → 81」这个倍数太漂亮，反而更需要怀疑：两次 Run 的模型输出本身有随机性，命令量的差异不可能全归给重复检测。

能说的只有：修复没有让它变差，且这道题这次解出了。要证明有效性，需要看这一批 41 道的整体结果——那是接下来要等的。

## 八、纠正：上面那个「1/13」的因果是错的

我在第七节把 `b7e57f9d`(1086 命令) → `a3275fd9`(81 命令) 的下降归给了重复检测。**逐条核对后，这个归因不成立。**

对本轮 3 个 Run 逐条重放「前 60 字符指纹」的最长连续重复：

| Run | 状态 | 命令 | fact | 最长连续重复 |
|---|---|---|---|---|
| `a3275fd9` BabySyc | SOLVED | 81 | 2 | **1** |
| `a5859b55` bestphp | SOLVED | 301 | 4 | **2** |
| `46de6a50` — | RUNNING | 344 | 0 | **2** |

**`REPEAT:5` 一次都没有触发。** 这些 Run 里最长的连续重复只有 2 条（`EOF` / heredoc 结尾符），离阈值差得远。

所以 BabySyc 这次用 81 条命令解出，是模型这一轮的输出本身更直接，**与我的修复无关**。

### 为什么和 `b7e57f9d` 的 1086 条差这么多

回看那个旧 Run 的形态：`33x /bin/bash -c "cd .../recon && python...`，重复是**同一个前缀但散落在流里**，不是严格连续。而我的检测只抓「连续相同」——**它抓不到这种间隔重发**。

这个设计选择当时是为避免误伤，但它让检测覆盖不到实际发生的那一类打转。

### 结论

- 修复没有害处（回归持平，3 个 Run 全部正常结束或仍在跑）
- 但它**尚未被证明有用**，在这批数据里触发率是 0
- 需要么（a）放宽到「滑动窗口内同一前缀出现 N 次」，要么（b）承认这条不是主要瓶颈

我倾向于 (a)：`b7e57f9d` 的 33 次同前缀出现在 1086 条命令里，滑动窗口能抓到，连续判断抓不到。但改之前得先确认这不是又一次「凭形态猜」。

## 九、第二条路也否掉了：滑动窗口去重

上一节说「倾向改成滑动窗口」，所以先回测再动手。

**回测设计**：对 2026-11-01 后完成的 40 个 Run，计算「15 条命令的窗口内，同一 60 字符前缀出现 ≥5 次」的首次触发位置。

| 状态 | Run 数 | 窗口检测会触发 | 触发率 |
|---|---|---|---|
| SOLVED | 23 | 8 | **35%** |
| UNSOLVED | 17 | 7 | **41%** |

**35% vs 41% —— 区分度基本为零。** 这会打断三分之一的成功 Run，却只多抓 6 个百分点的失败 Run。

对比当年校准 `stagnation_command_limit=40` 时的偏好：SOLVED 14% vs UNSOLVED 34%，2.4 倍。滑动窗口这条只有 1.2 倍，不够格上线。

**所以不改。** 现有的「连续 5 条」版本保留：它触发率低（这批 0 次），但至少不会误伤；等哪天有证据说明它抓到了东西再谈放宽。

### 一个更根本的判断

我在这一晚连续否掉了两条路（扩语料、加去重）。两次的模式一样：

1. 从个案观察到一个形态（4 道题同指令 / 50% 命令重复）
2. 假设这个形态是病因
3. 改成代码
4. 用数据检验，发现区分度不足

**个案的形态不构成病因证据。** 这跟 2026-11-08 那次「Drupal 读 22 次 POC 解出、Joomla 读 2 次没解出，看起来动人，484 Run 统计却无相关性」是同一个错误。

真正的下一步不是再加一个检测器，而是**先把这 38 道没跑过的题跑完**——在样本不足时继续调参，等于在噪声上做梯度下降。

### 四、已解题的真实开局长什么样（供将来写方法论文档）

## 十一、★★★ 重大纠正：常规题的真实解题率是 76%，不是 32%

### 我一直在用错的分母

之前每一份统计都写「常规题 19/58 = 32%」，把**从未真正跑过**的题也算成失败。

正确口径：只统计「存在过 `cmds > 0` 的 Run」的题。

| 类别 | 已解 / 尝试过 | 解题率 |
|---|---|---|
| CVE 题 | 53 / 53 | **100%** |
| 常规题 | **19 / 25** | **76%** |

「未解」39 道里，**33 道从未真正跑过**。

### 真正的能力缺口只有 6 道

```
Phuck2
[极客大挑战 2018]Comment
[极客大挑战 2019]Upload
[SUCTF2018]Unfinish
[De1CTF 2019]Giftbox
[STARCTF2019]996game
```

### 两个假样本源

1. **`NO_HEALTHY_WORKER_PROFILE`** —— 两个引擎体检都 `healthy: false`，Run 零命令，却被记成 `COMPLETED_UNSOLVED`。历史累计 80+ 次，2026-08 就有了。11-09 有 3 次，正是 Docker 挂掉那段时间。
2. **队列 PENDING** —— 题在排队，压根没轮到。

两者都会被读成「尝试过但解不出」。

### ★ 方法论铁律（补第 7 条）

**算任何解题率之前，先确认分母是「尝试过的题」，不是「库里的题」。**
判据：该题是否存在一个 `cmds > 0` 的 Run。

这跟已有的第 2 条（「统计前先确认被测代码真的跑过」——用代码 mtime vs `max(created_at)`）是同一类错误。那次我看 mtime，这次我看命令数；两次都把「没执行」当成了「执行后失败」。

### 为什么这一条比前面所有分析都重要

如果基线是 32%，剩下的 39 道全是能力问题，那我这一晚做的所有优化都有意义。

但基线是 76%：剩下 6 道，且每道都是独立的、无配方可循的怪题。**在这种情况下，任何「通用机制调整」的期望收益都接近零**——6 个样本撑不起统计检验，改一个参数很可能只影响 1-2 道题，而且方向不明。

这解释了我今晚为什么连续否掉两条路：不是我的假设本身太差，是**问题规模根本没那么大**。

真正的动作是把 33 道没跑过的题跑完，而不是继续调参。
