# 命令级停滞检测：让「原地打转」的 Worker 提前收敛

2026-11-06 14:40。比赛前的最后一项 agent 能力优化。

---

## 一、先否掉了两个看起来很像答案的假设

### 假设 A：成功的轮次读了更多本地 POC 库

第一眼很像：Drupal（82 条命令解出）读了 22 次 `/home/kali/pocs`，Joomla（397 条未解）只读 2 次，PHP 读 0 次。

**但全库统计推翻了它**（484 个 Run）：

| 读了几个不同 CVE 目录 | 轮次 | 解出 | 解题率 |
|---|---|---|---|
| 0 | 390 | 129 | 33% |
| 1 | 72 | 33 | 45% |
| 2 | 16 | 6 | 37% |
| 3+ | 6 | 2 | 33% |

没有正相关。Drupal 那次是个案——**不能凭一个个案改 prompt。**

### 假设 B：失败轮起步更慢

也不成立。首次利用尝试：SOLVED 中位第 **5** 条，UNSOLVED 中位第 **6** 条。重复命令率：5% 对 6%。**起点行为几乎一样。**

## 二、真正的信号

| 指标 | SOLVED (n=108) | UNSOLVED (n=172) |
|---|---|---|
| 平均命令 | 84 | **194** |
| 平均枚举命令 | 11.7 | **36.8** |
| 有枚举的轮次 | 79% | **91%** |

失败轮是成功轮的 2.3 倍命令、3.1 倍枚举。但**枚举本身不是问题**（成功轮 79% 也在枚举）——问题是它在失败轮里停不下来。

更直接的度量：**最后一次产生知识（事实 / deadend / 写下的发现）之后，还跑了多少命令？**

```
UNSOLVED 轮（n=22，有认知标记的）：
  平均总事件 236
  最后一次认知标记在 170
  标记后仍跑了 66 条（28%）
```

**28% 的命令产生于「已经什么都知道、也知道没戏」之后。**

PHP 那轮的具体形状：第 26 条命令写 `mark-deadend 'Flag not retrievable'`，之后 10 条重跑同样的 `find`，`--max-time` 从 40 → 60 → 90。

## 三、为什么现有三个限制都没拦住

| 限制 | 值 | 为什么失效 |
|---|---|---|
| `barren_limit` | 8 | 数的是**轮次**。三例全部只有 2 个 Worker 轮次 |
| `worker_max_turns` | 80 | 数的是 **turn**，一个 turn 可发多条命令 |
| `no_progress_timeout` | 0（禁用） | 是**墙钟**维度，且默认关着 |

关键数据：

| run | 命令数 | worker_started 事件 |
|---|---|---|
| Joomla `6712279f` | 703 | **2** |
| PHP `1b2a8586` | 74 | **2** |
| Drupal `e92b8431` | 164 | **2** |

`barren_limit=8` 永远等不到——**一个 Worker 可以在单轮内烧掉几百条命令，而轮次计数纹丝不动。**

## 四、实现

### 计数维度：命令，不是时间也不是轮次

`CoordinatorConfig.stagnation_command_limit = 40`。在 `_record_worker_step` 里每条命令都过一遍：

- `result_excerpt` 出现 `VERIFIED_FACT` / `DEADEND` / `FLAG` / `flag{` / `CTF{` / `CTF2{` → 重置计数
- 否则 +1，达到 40 → 请求收敛
- 触发后归零，避免收敛期间每来一条命令就再请求一次

### 动作用 converge，不是 stop

复用已有的 `request_convergence`——和 deadline 用的是同一个机制。**在飞的那一轮仍然跑完、仍然能写下它学到的东西**，这正是 convergence 与硬停止的分野。

### 阈值 40 是怎么定的

按「连续多少条命令没有新事实」统计算 484 个 Run：

| 阈值 | 触发 SOLVED | 触发 UNSOLVED | 偏好比 |
|---|---|---|---|
| 30 | 21% | 40% | 1.9× |
| **40** | **14%** | **34%** | **2.4×** |
| 50 | 10% | 28% | 2.8× |
| 60 | 8% | 25% | 3.1× |

选 40：误伤成功轮 14%，命中失败轮 34%。而且即使误伤，converge 也只是收尾，不是杀死。

中位数对照：SOLVED 最长无进展片段中位 **8** 条（p75=25），UNSOLVED 中位 **14**（p75=60，p90=114）。40 落在成功轮的 p90 附近，是合理的安全边界。

## 五、踩到的坑

**`config` 属性不存在时炸掉 step 回调。**

`test_muteki_worker_step_observability.py` 用 `object.__new__` 构造 Coordinator 但不设 `config`（它只测记录逻辑）。我最初写的是 `getattr(self.config, ...)`，直接 `AttributeError`。

关键点：**step 回调是绝不能抛异常的那条路径**——它从 Worker 线程调进来，抛了就把整条观测链断掉。改成两级 `getattr`：

```python
config = getattr(self, "config", None)
limit = int(getattr(config, "stagnation_command_limit", 0) or 0)
```

同时 `_stagnation_lock` 也做成惰性属性，因为 `threading.Lock` 不能作为类属性共享，而 `object.__new__` 不跑 `__init__`。

## 七、这轮优化到底改变了什么

**之前**：一个 Worker 可以在一轮里跑 700 条重复命令，而所有守卫都在数「轮」和「turn」，什么都没触发。

**之后**：连续 40 条命令没产生任何新知识就请求收敛。按历史数据，这会在 34% 的失败轮上提前收手，同时只碰 14% 的成功轮。

**没做到的事**：这不会让失败轮解出题。它只是把「已经知道没戏还在烧」的那 28% 命令还回来——省下的时间留给下一道题。
