前置：2026-11-06 凌晨三轮跑题验证，三条载荷全部被采纳、一条 RCE 确认打通，但 `verified_solve` 仍是 0。

## 一、路线 2 的前提被数据推翻了

原假设是「Worker 打通之后不知道怎么拿 flag，所以缺 `post_exploitation`」。

**先去验证了假设，结果不成立。** 用三条 Run 的实际命令比对 `EXECUTION_CHECKLIST` 的四步：

| checklist 步骤 | `1b2a8586` 是否执行 |
|---|---|
| `printenv` / `env` | ✓ |
| `ls -la /` / `ls -laR` | ✓ |
| `grep -rIl 'CTF2{'` | ✓ |
| `/proc/1/environ` | ✓ |
| 查 `disable_functions` | ✓ |

**四步全做了。** 所以不是「不知道怎么做」。

真正的问题是换一个：它做完了、判定了、然后不停止。

```
第 26 条命令（共 36）：mark-deadend 'Flag not retrievable on CVE-2012-1823 target'
之后 10 条命令：重新跑同样的 find / 和 strings /proc/*/environ
               把 --max-time 从 40 加到 60 再到 90，像在等一个更长的超时能改变答案
```

Joomla 那轮更糟：**397 条命令，从头到尾没写过一条 deadend**。

## 二、路线 2 实际做的两件事

### 1. `DEADEND_DISCIPLINE`：deadend 是承诺，不是日志

`backend/app/services/known_exploit.py` 新增，随 `EXECUTION_CHECKLIST` 一起注入 `AGENTS.md`（独立 marker，各自幂等）：

- deadend 之后**不许再发同一请求的变体**，加大 `--max-time`、换引号、加 header 都算同一件事
- 唯一例外是**新机制**而非重试：不同的代码路径、不同的权限、不同的文件——而且必须先用一行说明差在哪
- 只剩重试时**停下来报告负面结果**：8 分钟收尾的「RCE 确认，flag 不可读，这些是查过的」比 26 分钟重复失败有价值

### 2. `post_exploitation`：按技法给「拿到原语之后」的路径

`scripts/fill_post_exploitation.py`，478 条全部填充（原本全是 `[]`）。

关键约束来自渲染器：`_render_entry` 只打印**前 3 条**、每条**200 字符**，超出静默丢弃。所以每一步都是自带命令的独立指令。

分两层，产品特化优先于技法：

- **技法层**（10 类）：sqli / rce / path-traversal / lfi / deserialization / auth-bypass / xxe / ssrf / file-upload / injection / ssti
- **产品层**（3 个覆盖）：joomla、phpmyadmin、weblogic

Joomla 的覆盖是直接针对昨晚的失败：

> 1. SQLi 只是入口：先 `select user,authentication_string from <db>.users` 拿管理员口令哈希，再用它登录 `/administrator` 后台。
> 2. 后台的模板编辑器可直接写 PHP：Extensions → Templates → 编辑 index.php，插入 `<?php system($_GET[c]);?>`，然后 `?c=id`。
> 3. 有了命令执行再 `printenv | grep -i flag` 与 `grep -rIl 'CTF{' /var/www /tmp` —— **flag 在文件系统，不在 joomla 库里。**

昨晚它读了 `version()` / `database()` 之后就在数据库里找 flag，找了 397 条命令。

## 三、路线 3：排队器现在看历史

### 数据支撑

| ACTIVE 题分桶 | 数量 |
|---|---|
| 从没跑过 | 0 |
| **跑过，从未解出** | **119** |
| **历史上解出过** | **14** |

133 道 ACTIVE 题全部跑过至少一次。**最常见的情况不是「未知」，而是「已经测过不行」。**

`[PHP]CVE-2012-1823` 就在第一类：5 次 Run、0 次解出，而 prompt 里早就记着原因。昨晚我在它身上花了 25 分钟。

### 实现

`_order_by_history()`，在 `_candidates` 取到 PENDING 后、`_flagless_platform_ids` 过滤前调用：

```
solved > 0        →  最前   （再跑一次最可能出样本，正是 verified_solve 需要的）
never run         →  中间   （未知，值得给格位）
runs > 0, solved=0→  最后   （已经被测过一次不行）
```

**不改 `priority` 列**——那是操作者的意图。用桶排序，桶内保持原有 `(priority, created_at)` 顺序（稳定排序），所以手动置顶仍然有效。

只读历史，不回写任何东西：启发式判断错了最多排错一批，不会污染「实际发生了什么」的记录。

### 真实数据验证

用真实 async session 跑 130 条队列行（临时视为 PENDING）：

```
排序前 (runs, solved):  (1,0) (1,1) (3,0) (2,0) (2,1) (2,0) (1,0) (1,1)
排序后 (runs, solved):  (1,1) (2,1) (1,1) (3,1) (3,1) (1,1) (3,1) (1,1)
```

`solved=1` 的全部提到最前，`solved=0` 的全部沉底。**排序生效。**

（中途用 fake session 测时看起来「没生效」，原因是 fake 忽略了 `where` 条件、把全量 stats 都返回了——是实现之外的测试假象，真实 SQL 正确。）
