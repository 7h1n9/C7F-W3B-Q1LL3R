# L1 落地方式：A/B 实验不可行，改为四阶段渐进

2026-11-05 晚。承接 `docs/notes/2026-11/2026-11-05-L1-first-move.md`。
**结论：原方案（10 题 A/B 比步数）做不出结论，已放弃。改用四阶段渐进，每阶段有独立判据。**

---

## 一、原方案为什么不行（数据判死的，不是感觉）

### 障碍 1：噪声是信号的 2 倍

用 500 个 Run 的历史数据算题内波动（同一道题重复跑）：

| 指标 | 值 |
|---|---|
| 题内波动（首次利用步数极差） | 中位 **12** 步，均值 21，最大 60 |
| 组间差异（解出 vs 未解中位） | **6** 步 |

**要检出 6 步的效果，按 α=0.05、power=0.8 粗算，每臂需 ≈74 个 Run。**
两臂 148 次 × 约 20 分钟 ≈ **49 小时**，还要靶机全程存活。

### 障碍 2：环境配额硬性为 1

```
quotas = {max_environments: 1, active_environments: 0,
          read_requests_per_minute: 120, write_requests_per_minute: 30}
```

`arena.py:380` 的注释写得很清楚：这是 **"capacity 1" 是事实而非假设**。
所以"两个后端并行跑两臂"的设计不成立，只能串行——总时长翻倍或更多。

### 障碍 3：单次 Run 基本是抛硬币

同题重复跑的解出率：

| 题目 | 次数 | 解出率 |
|---|---|---|
| `[HITCON 2016]Leaking` | 10 | **0%** |
| `Weblogic CVE-2018-2628` | 10 | 10% |
| `Sentinel-1B` | 16 | 12% |
| `企业运维日志归档中心` | 7 | 42% |
| `[LOCAL]PHPMYADMIN` | 4 | **75%** |

### 障碍 4：温度不可控

Worker 是外部 CLI（codex/claude），采样温度由 CLI 决定，项目侧没有参数可调
（`container_exec.py` / `official_worker.py` 里搜不到 temperature）。所以不能靠
`temperature=0` 去压噪声。

## 二、顺带查出的 L1 实际错误（已修）

`FIRST_MOVE_DISCIPLINE` 原本让 agent 把假设写进 `notes/hypothesis.md`。
**那个目录是死的**——全库 652 个 workspace 里：

| 位置 | 出现的 workspace 数 |
|---|---|
| `.muteki_board.md` | **67** |
| `muteki/CLAUDE.md` | 564 |
| `notes/` 下的任何文件 | **1** |

真正的事实通道是 Blackboard：`python3 "$MUTEKI_BLACKBOARD_SCRIPT" write-fact '<json>' --verified`，
全库 21,424 条 `muteki.fact_added` 走的就是这条线。

**已改为**"在回复里一行说明计划并立刻去打"，不再指定死路径。改完 22 条相关测试通过。

> 教训：写约束时不能假设"某个目录自然会被用"。要先查历史 Run 实际写到哪。

---

## 三、替代方案：四阶段渐进，每阶段单独可判

不必一次证明"L1 提升解出率"。沿着从便宜到贵的阶梯走，每级拿到一个确定的结论：

### 阶段 0：零成本误判检查（现在就能做）

**做什么**：用现有 500 个 Run，检查 L1 想修的那种行为有多普遍。

**判据**：
- `installer_before_exploit` 占比 —— 若全库只有 6 条（2%+4%），说明"去修靶机安装向导"
  **不是主要矛盾**，L1 第 2 条对总分影响很小；
- `exploit_steps == 0` 的占比（已解 18% / 未解 19%）—— 这部分是"全程没试过利用"，
  才是 L1 第 1 条真正要覆盖的人群。

**产出**：判断 L1 的三条约束里哪条真正有用，砍掉没用的（避免 prompt 里塞无效内容）。

### 阶段 1：可观测性（1 次 Run，约 25 分钟）

**做什么**：跑 1 个 Run，确认 Worker **真的读到了** `FIRST_MOVE_DISCIPLINE`。

**判据**：该 Run 的 `AGENTS.md` 前 50 行含 `## Your first move`，且 `run_events`
里能看到 Worker 在动手前引用/复述了假设。

**意义**：这一步不做，后面所有实验都可能在测一个根本没被读到的文本
（历史教训：`AGENTS.md` 九种读法只有六种能读到头部）。

### 阶段 2：中期信号（10 个 Run，约 3–4 小时）

**做法**：单臂，全开 L1，跑 10 个 Run（挑历史解出过、极差小的题）。

**不看解出率**，看两个**比步数更硬的**中期信号：

| 信号 | 为什么比步数硬 |
|---|---|
| `exploit_steps == 0` 的比例 | 二值，不受"第几步"的噪声影响。历史基线 18–19% |
| `installer_before_exploit` 比例 | 二值。历史基线 2–4% |

**判据**：只能作为"方向性观察"，不能作为证明。10 个样本的结论我会明确标注为
"未达统计显著"。若这两个二值指标明显下降（如 0/10），值得进入阶段 3。

### 阶段 3：低噪声证伪（只在有明确信号时做）

**做法**：挑 3 道**极差 ≤7 步**的题（`Weblogic CVE-2018-2628` 极差 3、
`GXYCTF BabyUpload` 极差 7、`极客大挑战 HardSQL` 极差 7），每臂各跑 5 次。

**判据**：同一题内配对比较（配对消除题目难度差异），10 次 Run × 3 题 = 30 次，
约 **10 小时**。这是这套指标下能拿到显著性的最省方案。

---

## 四、建议的执行顺序

1. **阶段 0**（约 10 分钟，纯查询）—— 先确认 L1 三条约束哪条有用，可能直接砍掉一条
2. **阶段 1**（1 次 Run）—— 确认文本被读到
3. 若阶段 0 显示 `exploit_steps==0` 占比确实高（当前 18–19%），做**阶段 2**
4. 阶段 3 只有在阶段 2 出现明确信号时才投入 10 小时

**不推荐**：跳过 0/1 直接跑原计划的 10 题 A/B。那样最可能的结果是拿到一组
差值在噪声内的数字，然后花很长时间争论它算不算效果。

---

## 五、必须写下来的限制

- `installer_before_exploit` 全库仅 6 条，**Confluence 那个 88 步装环境的例子是极端个例**，
  不能当作 L1 的主要论据。我之前那样叙述是不准确的，已在此更正。
- 阶段 2 的 10 个 Run **不构成统计证据**。它能排除"完全没效果"，不能证明"有效果"。
- 阶段 3 即使做完（30 次 Run），统计功效也只在检出 **≥10 步**的效果时够用；
  6 步级别仍需约 74 次/臂。

# 阶段 0 结果（21:47 跑完）：L1 三条约束里只有一条站得住

用 277 条有命令记录的 Run（500 条样本中筛出）核查三条约束的真实覆盖面。

## 结论一览

| L1 约束 | 覆盖面 | 判定 |
|---|---|---|
| ① 事实→假设，立刻去打 | 真正"全程无任何攻击形态"的至多 **30/277 = 10.8%** | **勉强可用，但远小于原估** |
| ② 靶机安装状态不是目标 | **10/277 = 3.6%**（已解仅 2 条） | **应删除** |
| ③ 8 步死路就换路 | 阈值 20 步时 72/277=26%，但**题内波动中位 12、最大 60** | **阈值在噪声内，不可靠，应删除** |

## 关键发现：`exploit_steps==0` 里一半是"已解"

60 条判为"从未利用"的 Run 中，**30 条是已解的**。逐条查命令发现它们确实在利用，只是形态不在我的检测器里：

| 未覆盖形态 | 命中次数 | 实例 |
|---|---|---|
| 逻辑/cookie 篡改 | 21 | `BuyFlag` 改 `user=1` + `money=1e9`；`Kookie` 用登录 cookie |
| SQL 非标准载荷 | 9 | `SUCTF EasySQL` 用 `1\|\|1#`，不是 `union select` |
| 文件/备份泄露 | 54 | `.bak` / `.git` / `www.zip`（这类还混着 github 搜索，需要人工分） |
| 命令执行原语 | 10 | `system()` / `passthru` / `${IFS}` |
| 反序列化编码 | 3 | `O:4:` / `unserialize` |

**所以 `exploit_steps==0` 这个指标本身不纯**：它把"逻辑漏洞型利用"误判成"没利用"。
如果拿它当阶段 2 的判据，测出来的差异可能是检测器的偏差，不是 L1 的效果。

## 更重要的是：问题规模比以为的小得多

我之前把"第一轮判断质量"当成主要矛盾，依据是 Confluence 那条 88 步装环境的极端轨迹。
阶段 0 显示：

- 装环境问题：3.6%，个例
- 全程不攻击：≤10.8%
- **剩下约 85% 的 Run 是在正常攻击、正常失败**

也就是说，L1 想覆盖的人群只有 10% 左右。而昨天算过，检出 6 步效果需要每臂 74 个 Run。
10% 的人群 × 每臂 74 个 Run ⇒ 需要约 **700 个 Run 才能看出效果**。
这条路在经济上不成立。

## 修正后的判断

**L1 的价值不在"提升解出率"，而在"减少无效步骤"。** 这两件事要分开：
- 提升解出率：需要 700+ Run 才能验证，不可行；
- 减少无效步骤：可以用**单 Run 内**的指标直接看（同一 Run 里，装环境/漫游的步数占比），
  不需要跨 Run 统计，因此不受题内波动影响。

## 建议

1. **删掉 L1 的第 2、3 条**（3.6% 且 26% 阈值在噪声内），只留第 1 条，
   并把 wording 收窄到"拿到版本号后先试已知 exploit，再考虑其它"。
2. **先补检测器的逻辑漏洞形态**（cookie/参数篡改、非标准 SQLi），
   否则任何用它做的比较都不可信。
3. **不要再用"每臂 N 个 Run 比步数"的思路**。改用单 Run 内的步数构成
   （`installer_steps / total_steps`、`explore_steps_before_first_exploit / total_steps`），
   这是配对指标，天然消除了题目难度和题内波动。
