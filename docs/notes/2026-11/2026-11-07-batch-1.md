## 二、两道解出的归因

### Couchdb `bd2d60a2`（766s）

载荷 `PUT /_users/org.couchdb.user:vulhub`（`roles: ["_admin"]`）→ 提权成功 → 读到 `_config` → 注入 `query_server` → RCE → 读 `/proc/1/environ` 拿 flag。

**载荷是必要前提**：`_config` 和 `query_server` 都需要 admin 角色。

### ElasticSearch `4744b233`（215s，最快）

**15 条命令，10 条用载荷（67%）**，第 27 个事件就拿到 flag。

它用载荷的 groovy 执行写了 `/tmp/rd.py` 读文件工具，直接读 `/proc/1/environ`。

**这是目前最高效的一次**——载荷质量 + checklist 的 flag hunt 步骤配合得很好。

### 归因三条件（每个都是踩出来的）

**1. 产品/CVE 必须对得上**

第一版只按 token 重叠，把 `drupal:7600` 归给了任意 Drupal 题。

**2. 稀有 token（df ≤ 2）**

通用参数是词汇不是指纹：
- `_drupal_ajax`、`element_parents` —— 任何 Drupal 题都会用
- `_users/org.couchdb.user` —— 只有这一条载荷有

**3. 响应必须是「活的」**

有执行痕迹（`uid=` / traceback / `"rows"`）**且不是**应用自己的页面（`form_build_id` / `<html` / login）。

这是唯一能区分「载荷跑了」和「载荷发了被忽略」的信号。

## 五、踩到的 schema 坑

`trust_level` 和 `provenance` 都是**封闭 schema**：

- `trust_level: Literal["reviewed", "curated", "unverified"]` —— 写 `"verified"` 直接 ValidationError，一次挂了 13 条测试
- `provenance` 是 `extra="forbid"`，只有 4 个字段（`source_type` / `source_ref` / `source_url` / `notes`）

所以 Run id 只能进 `provenance.notes` 的自由文本，写成 `verified by run <id> (accepted flag)`。

## 六、环境问题（已解决）

### 控制面接收器有 ~15 秒启动延迟

两次 `FAILED_ENGINE` 报 `control plane unreachable`。查了很久以为是 bind 配置错，最后**实测监控**发现 9100 端口在**第 15 秒才出现**，且是正确 `0.0.0.0:9100`。

`ControlReceiver.instance()` 是**按需启动**（首次进入 container 模式），不是后端起来就开。

**教训：Run 刚启动的 15 秒内不要下结论。**

### 脚本连 DB

```bash
APP_DATABASE_URL="mysql+asyncmy://ctf_agent:ctf_agent@127.0.0.1:3307/ctf_agent"
```
是 **3307 不是 3306**，且必须 unset 所有 proxy 变量。
