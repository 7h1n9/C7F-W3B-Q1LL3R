2. 有 4 次在读 `docker-compose.yml` / `Dockerfile` —— 这是在**从靶机构建文件反推环境**，说明 README 给的信息不够。

## 六、诊断结论

失败的主因不是"不会规划"，而是**手里没有可直接套用的具体 payload**：

- 我们的 `payload-corpus.jsonl` 只有 **6 条**（6 种技法各 1 条），全部 `unverified`
- `cve-playbook.jsonl` 只有 **20 条**
- 而 worker 实际能读到的 `pocs/vulhub` 是**通用 CVE 说明**，不是针对本平台的利用细节

所以 87 条命令 → 4 条事实的根因是：**每条命令都在重新发明 payload**，
而不是"查一个已验证的 payload，改占位符，打出去"。

## 七、因此 A 方案（从已解 Run 反推 payload）是对的方向

| 现状 | 目标 |
|---|---|
| 6 条 unverified payload | 从 144 道已解题 × 平均 5 条决定性命令 ≈ 数百条 **verified** payload |
| 每条命令重新发明 | 查表 → 改占位符 → 打 |

而且用已解 Run 反推有三个别的方法没有的优点：
1. **与靶机同源**：payload 是在同一套 `direct-ctf2` 环境里真的打通的；
2. **含失败边界**：同一条 payload 在哪些情况下失败，历史 Run 里有记录；
3. **零外部依赖**：不依赖网络、不涉及爬取合规问题。
