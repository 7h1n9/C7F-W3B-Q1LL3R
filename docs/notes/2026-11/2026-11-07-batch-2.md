## 三、`verified_solve` 7 → 12

新增 5 条：`1panel:39907`、`jackson:7525`、`langflow:3248`、`n8n:21858`、`rails:5418`。

### 判据又调了一轮（真实 miss 驱动）

第一版的 live 判据只认 shell 痕迹（`uid=` / traceback / SQL 错误），**误杀了两道真解出的题**：

**1Panel `965c1875`** —— 载荷的登录绕过返回
```json
{"code":200,"message":"","data":{"name":"1panel","token":"","mfastatus":""}}
```
外加 `psession` cookie。登录成功了，但没有 shell、没有报错，被判成死的。

**GhostScript `8d56bfab`** —— 响应是
```
200 134 <form method="post" enctype="multipart/form-data">
```
上传页正常返回自己的表单，被 `_DEAD_REPLY` 里的 `<html` / `<form` 判成「应用重新发了页面」。

修法：
- `_LIVE_REPLY` 增加结构化 API 响应标记：`"code":` / `"data":` / `"token"` / `psession` / `multipart/form-data` / `file_upload`
- `_DEAD_REPLY` 收窄到真正表示「页面回来了」的标记：`form_build_id` / `form_token` / `404` / `503` / `502`

### 两条仍然无法归因，而且是对的

**GhostScript `8d56bfab`**：载荷的 token 全部太通用——
| token | 出现条目数 |
|---|---|
| `index.php` | 11 |
| `form-data` | 15 |
| `tmp/success` | 38 |

**没有任何一个能证明 Worker 用了这条载荷而不是自己想到的。**

**Apache Cxf `d1ae80b6`**：有 df=1 的 token（`etc/hosts`、`related`、`service.namespace`），但都没在命令里出现。

**这是判据的正确行为，不是 bug。** 宁可漏标，不能错标——错标会让 `_pick_entries` 把未验证的配方排进 FIRST ACTION。

## 四、新增工具：靶机监控

`scripts/watch_dead_targets.py`。第一轮在两台 503/502 上烧了 52 分钟，这个脚本就是为了不再重复。

```
python scripts/watch_dead_targets.py --interval 25 --grace 90 --strikes 3
```

- 每 25 秒查一次 RUNNING 的 Run，读 `challenges.target_url` 探活
- 只把 **5xx / 连接失败** 算死；401/403/404 是活着的应用
- 一次正常响应清零计数（容器刚起来可能 502 一次）
- 连续 3 次死 → 调 `/api/v1/runs/{id}/cancel`，队列换下一道

**本轮没触发**（五道靶机都活着），所以它还没在真实失败场景下验证过。
