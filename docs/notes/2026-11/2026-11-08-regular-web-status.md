**它卡在哪**

## 五、常规题的真正瓶颈（按证据排序）

### 1. 多阶段链的深度超出单轮预算（主因）

常规题（尤其国内赛 Web）典型结构是 3-5 跳：`源码审计 → 弱凭据 → 上传 → 路径预测 → 二进制/反序列化 → flag`。
CVE 题通常 1-2 跳（发一个已知 payload 就有回显）。

当前 `RUN_CONVERGENCE_SECONDS=120` + worker 单轮额度，够走完 2 跳，不够走完 5 跳。

### 2. 每跳之间缺少「已确认状态」的压缩

两个 worker 各跑 100+ 条命令，但 fact 只有 9 条。多阶段题的关键是**把前一阶段的结论固化成下一阶段的输入**，现在这一步靠 worker 自觉写 `VERIFIED_FACT`，覆盖率不足。

### 3. 二进制/编译类构造能力缺失

`滑稽云音乐` 需要现场编译 ELF；`[SCTF2018]BabySyc`、`[RCTF 2019]Nextphp` 也涉及非标准 payload 构造。容器里有 `gcc`/`python3` 但缺「给定目标 ABI 就生成可用 .so」的成型配方。

## 六、与 CVE 题的差异本质

| | CVE 题 | 常规题 |
|---|---|---|
| 知识来源 | 公开 CVE 语料（645 条配方） | 无，必须现场审计 |
| 利用跳数 | 1-2 | 3-5 |
| 每跳的信息 | 配方直接给 | 必须自己从响应推断 |
| 本轮提升 | 1 → 27 覆盖，68% 解出 | 无变化（21%） |

**探针通道对常规题完全无效**——因为它依赖「标题里的 CVE 命中语料」。这就是 46 道常规题探针覆盖率 0 的原因。

## 七、可行的下一步（不改 prompt，改结构）

1. **给常规题放宽单轮预算**：多阶段题需要更多命令额度，可以在识别到「已进入利用阶段」（有 ≥2 条真实 fact）时延长收敛窗口，而不是一刀切 120s。
2. **强制阶段交接**：每完成一个可利用阶段，要求 worker 输出结构化的「当前能力 + 下一个目标」，而不是自由叙述。
3. **建常规 Web 技法库**：不是 CVE 组织，而是 `攻击面 → 检测动作 → 利用动作`。这是唯一能覆盖 46 道题的方向，但工作量大。
4. **二进制构造配方**：`滑稽云音乐` 这类需要现场编译的题，单独做一层「目标 ABI → 可用 payload」的模板。

## 九、多阶段预算自适应（2026-11-09 实现）

### 改了什么

`CoordinatorConfig.stagnation_command_limit`（连续多少条命令没有新 fact 就触发收敛）从**固定 40** 改为**随已产出 fact 数增长**：

```
limit = 40                                    if facts <= 2
limit = min(140, 40 + 20 * (facts - 2))       if facts > 2
```

- `facts <= 2` 完全不变 → CVE 题（1-2 跳，68% 已解）不会被拖慢
- 有进展才延长 → 不是按时间、不是按命令数，只按「已经证明自己能学到东西」
- 上限 140 → 防止靠刷廉价 fact 无限续命

配套：`_stagnation_fact_count` 用 2 秒 TTL 缓存（这条路径每个 Worker 命令都会走一次，不能每次都查 SQLite）。

### 为什么 40 对多阶段题是错的

40 这个数字是对 484 个 Run 校准出来的（SOLVED 触发 14% / UNSOLVED 34%），校准本身没问题——但那个样本被**单跳题**主导，在单跳题里「40 条命令没学到东西」确实等于在打转。

多阶段题的阶段之间，命令量大但 fact 数为零是**结构性的**：

| 阶段动作 | 典型命令量 | 是否产出 fact |
|---|---|---|
| 指纹识别 | 2-5 | 是 |
| 源码审计（clone + 读） | 10-30 | 是 |
| 弱凭据爆破 | 5-30 | 是 |
| **文件名 oracle 推导** | **30-100** | **否（直到成功）** |
| **md5 爆破 10^6** | **1-5（脚本内）** | **否** |
| **编译 ELF .so** | **50-200** | **否** |

最后三行每行都能独立触发 40 条上限。

### 实测依据

46 道未解常规题：**33 道（72%）已有 ≥2 条真实技术结论**，20 道已用满 3 次重试。
代表样本 `滑稽云音乐` 已拿到 admin 密码 + 确认上传 + 解出文件名 oracle，死在 ELF 构造。

### 还没做的

- 收敛**窗口时长**（`RUN_CONVERGENCE_SECONDS=120`）没改。改它涉及 deadline 算术，风险高于收益，先看命令额度这一层够不够。
- 二进制构造配方（「目标 ABI → 可用 payload」）未做。

## 十一、又发现并修掉一个让计数器完全失效的洞

Run `a6251f12` 跑到 **296 条命令 / 0 条 fact / 仍 RUNNING**。0 fact 的 Run 本该在 40 条命令时收敛，实际跑到了 296。

**根因**：`learned` 标记列表里有一个**裸 `"FLAG"`**。Worker 找 flag 时输出里到处是这个词：

```
find / -name '*flag*'      → find: '/proc/1/flag': no such file
grep -r flag /var/www      → ...
cat /flag                  → ...
```

154 条 tool_result 里 17 条含 `FLAG`，**每一条都把计数器清零**。计数器从未累计到 40。

**修法**：`"FLAG"` → `"FLAG="`，并补 `"FLAG{"`。判定「有进展」的标记必须是**结构**（`VERIFIED_FACT`、`DEADEND`、`FLAG=`、`flag{`），不能是**名词**。

### 这条教训的普适性

同一个文件里，`_fa_is_move` 的 `_FA_SHELL` 也曾漏掉 `ssh`/`scp`，导致 Git 那道题的探针一直下发不了。两次都是「匹配列表不完整/过宽」，而且都静默失效——不报错、不告警，只是行为悄悄错了。

**这类缺陷只能靠「拿真实 Run 的行为去核对设计意图」发现，读代码看不出来。**
