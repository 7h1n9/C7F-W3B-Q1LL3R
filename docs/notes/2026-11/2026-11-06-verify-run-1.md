## 一、先踩了三个坑才跑起来

### 坑 1：已解题无法重跑

第一次选了 `[ElasticSearch]CVE-2014-3120`（已解），retry 后状态秒回 `SOLVED`，没有新 Run。根因在 `arena_solve.py:663`：

```python
if detail.get("is_solved"):
    outcome.verdict = VERDICT_ALREADY_SOLVED
    outcome.run_status = "SKIPPED_ALREADY_SOLVED"
    return outcome
```

平台侧记录该 agent 已解过，**直接跳过，不消耗环境格位**。所以②必须用**未解过的题**，不能用已解题做「有 ground truth」的验证。这推翻了我原本的选题策略。

### 坑 2：调度器空转，`current_item_id` 恒为 null

`queue/start` 返回 `already_running` 但 `current_item_id: null`，条目一直 PENDING 不跑。根因在 `arena_queue.py`：

```python
current = arena_lease_manager.current
if current is not None and not current.released:
    return None      # ← 有残留租约就永不取题
```

`arena_lease_manager.current` 是**内存对象**，`run_execution_leases` 表里查不到。**只能重启后端**。重启后 `state: started`，立刻正常。

### 坑 3：retry 的 commit 有延迟

`queue/bulk {"action":"retry"}` 返回 `changed:1`，但紧接着查数据库仍是 SOLVED。等一次再查才变 PENDING。**不要用「调用后立即查」判断成败。**

## 三、失败原因分三层，每层都是真问题

### 第 1 层：curl glob 陷阱（已修）

```
curl: (3) bad range in URL position 95:
  ...&list[fullordering]=updatexml(...)
```

`list[fullordering]` 的方括号被 curl 当作 **glob 范围**。Worker 把 `GET ... HTTP/1.1` 转成 curl 时没加 `-g`，第 2 和第 17 步全废在这。

**这是载荷自身邀请的错误**：43/478 条含 `[param]` 形态。已改为在提取时**百分号编码**：

```
list%5Bfullordering%5D=updatexml(...)
```

对 PHP 是同一个参数，对任何 shell 都是惰性的。不影响路径里的方括号（`/a[b]/c` 不动）。

### 第 2 层：靶机停在安装向导（21% 的命令耗在这）

加 `-g` 后拿到：

```
HTTP/1.1 302 Found
Location: /installation/index.php
```

Joomla 容器没装完。Worker 花了 86 条命令在安装向导上（`/installation/index.php`、建库、建管理员），最后放弃。

**这印证了 L1 第 2 条约束**（「靶机安装状态不是你的目标」）。但注意：这条约束在 2026-11-05 的阶段 0 里被我用「3.6% 覆盖面」的数据删掉了。**这次单例把它从 3.6% 顶回来了**——不是推翻统计，而是说明它命中时会吃掉 21% 的预算。

### 第 3 层：SQLi 打通了，但 flag 不在数据库里

第 101 步之后：

```
### updatexml(1,concat(0x7e,version(),0x7e),1)
500 size=2687
XPATH syntax error: '~5.7.28~'
```

**注入是成功的**，能读 `version()` / `database()`。但 Joomla 的 flag 通常在文件系统（`/flag`、`/tmp/flag`），不在 `joomla` 库里。载荷教的是「怎么注入」，没教「注入之后去哪拿 flag」。

## 五、为什么 `verified_solve` 仍然是 0

`verified_solve` 的语义是「这条 recipe 在本平台靶机上真的拿到过 accepted flag」。这一轮没有 flag，所以**一条都不能标**。

标了就是造假，而造假会让 `_pick_entries` 把一条未验证的载荷放进 FIRST ACTION 槽位——那正是 `models.py:44-52` 那段注释里记录的旧事故（S2-009 的 `/ajax/example5` 配方「内部一致、通过所有 schema 检查、但对这个实例是错的」）。

---

## 六、要真正拿到 `verified_solve`，需要什么

1. **靶机必须是装好的**。Joomla 这条大概率是个坏靶机，换题比硬啃划算。
2. **载荷要带 post-exploitation**。SQLi 打通之后得知道去哪读 flag；现在所有导入条目 `post_exploitation` 都是空数组。
3. **至少 3 题成功**才够看趋势（题内波动中位 12 步，单题单次是噪声——这个结论 2026-11-05 已经算过）。

按 25 分钟/题、单环境格位串行算，3 题 ≈ 1.5 小时，加上失败重试，4 小时窗口最多跑 5-6 题。**这一夜能验证到的上限就是个位数**，不足以把 478 条语料变成可信。

## 这是三轮里载荷效果最好的一次

| 指标 | 值 |
|---|---|
| 总命令 | 36 条（三轮里最少） |
| **使用我们载荷的步** | **16 次**（seq 20,24,26,28,35,37,41,42,48,49,55,56,63,64,69,70） |

载荷是纯 HTTP POST（`?-d+allow_url_include=on+-d+auto_prepend_file=php://input`），不依赖 ysoserial 之类的外部工具，**直接可用**。

## RCE 确认打通

seq 20 的响应拿到了 phpinfo 的关键项：

```
disable_functions   no value
open_basedir        no value
```

两者都为空 ⇒ 命令执行不受限。随后 Worker 把它包成 `rce.sh` 复用（`shell_exec(base64_decode(...))`），说明它认这条载荷是可靠的。

## 为什么还是没拿到 flag

最后 16 次载荷全在找文件：

```
system("find / -iname \"*flag*\" ...")
system("strings /proc/17/environ /proc/18/environ ...")
system("find / -xdev -newer ...")
```

**命令能执行，但 flag 不在它能读到的位置**，或者 `find` 全盘扫描超时（`--max-time 90` 仍不够）。

## 对 `verified_solve` 的结论

**仍然只能是 0。**

三条载荷都进了 `AGENTS.md`、都被大量使用、其中一条确认生效，但没有一条**导致 flag 被取到**。

`verified_solve` 问的是「这条 recipe 拿到过 flag 吗」，不是「这条 recipe 能用吗」。这个区分是刻意的（`models.py:44-52`：S2-009 那条配方「内部一致、通过所有 schema 检查、但对这个实例是错的」仍占据 FIRST ACTION 槽位，把弱模型引进了死胡同）。

要放宽这个定义就是自欺：一旦「载荷被采纳」算数，`_pick_entries` 就会把未验证的条目排进 FIRST ACTION，而那正是这段代码当初要修的问题。

## 三轮真正学到的东西

1. **载荷采纳率极高**：三条全部被采纳，最早第 2 步、第 20 步就开始用。B 的「让 Worker 拿到可执行请求」这个目标**达成了**。
2. **采纳 ≠ 解题**：失败点全部在**载荷之后**——靶机没装完、版本不匹配、flag 位置未知。这三个都不是「载荷质量」问题。
3. **`post_exploitation` 全是空数组**：这是导入条目的结构性缺陷。三条都卡在「打通之后去哪拿 flag」，而语料对此一个字都没说。
