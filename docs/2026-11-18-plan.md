## P0：FA（首行动）—— 2026-11-18 实测后已重定性

### 概念
FA = 在 worker 起跑时，把一条**可直接执行、直接打在靶机上的具体动作**（完整 exploit 请求 / 载荷 / 命令序列）注入到 exploit lane 的首条消息里，替代「先做一轮通用侦察」的默认开局。

### ★★★ 实测结论（2026-11-18，数据库在线，可直接复算）

| 事实 | 数值 | 来源 |
|---|---|---|
| 事件真实名称 | **`muteki.exploit.first_action`**（`EventBridge` 统一加 `muteki.` 前缀） | `adapter/event_bridge.py:53,56` |
| 历史注入总量 | **5 条 / 5 个 Run**（11-08×3、11-09×1、11-12×1），全在 `exploit:known-path` lane | `select ... where event_type='muteki.exploit.first_action'` |
| 同期 Run 总量 | 121 个（11-08~11-12 `worker_started`） | 同上 |
| **注入率** | **约 4%** | 5/121 |
| **供给率（当前待跑 47 题）** | FA 非空 **1 道（2%）**；有 CVE 但 FA 空 18 道（38%）；无 CVE 且空 28 道（59%） | 直接调 `exploit_first_action()` |
| CVE 轴命中 | 那 18 个 CVE 标识调 `first_action_for_cve()`：**0 命中** | 同上 |

**三条被推翻的判断（不要再沿用）**：
1. ~~「`exploit.first_action` 事件 0 条，注入代码从未执行」~~ —— 是**查询漏了 `muteki.` 前缀**。事件存在，只是极少。
2. ~~「6.5 倍是 FA 的因果效应，只差曝光」~~ —— 143 是**「有 FA 可用的题目数」**（`known_exploit.py:1253,1785` 注释原文即 "143 Challenges that had a FIRST ACTION"），不是注入次数。而注入历史仅 5 个 Run。**该统计从未测量过注入效应**，它实际度量「这题被知识库理解过」。
3. ~~「改 `lane_key.startswith("exploit:")` 门条件或扩 lane 能提高指标」~~ —— 门条件是设计（exploit 是 index 0），且单引擎 `:1879`、race `:1934` 两条路径**都已正确接线并记录事件**。改它不会提高任何指标。

### 重定性后的结论
**瓶颈在知识供给（LD 层），不在注入机制。** FA 机制本身已完成、正确接线，但上游几乎无货可注（2%），因此：
- 机制的可达上限 ≈ 2% 的题，**不能**外推成「上线后解出率会涨」。
- 这条与「能力层 69% 空白」是**同一个问题**：`first_action` 依赖配方/CVE 命中，而配方覆盖率极低。P1 的语料建设优先级应高于任何 FA 代码改动。

### 仍然值得做的实验（范围必须收窄）
20 题随机对照（实验组**人工写入** FA，绕开供给）仍可做，但它回答的是：
> 「给一个本来没有 FA 的题硬塞一条正确首行动，能否提升解出率」

它**不回答**「扩大 FA 覆盖能否提升整体解出率」——后者受供给率 2% 限制，做出来也无法上线兑现。预注册文件 `experiments/fa-causal-v1.yaml` 需补一条「结论适用范围」声明，否则又是一次「产出≠生效」。

### 供给率是 P1 的度量前置
`scripts/prepare_fa_causal.py` 已可产出分组名单；分组时会排除历史有 FA 的题，但**建议在选样阶段就直接排除「供给率为 0 且无法人工补」的题**，否则实验组写不出 FA。

### 实验设计（`fresh_reproduction_verified=0` 之外的第二个高优先实验）
1. 从 ACTIVE 122 道里取 **20 道当前无 FA** 的题。
2. 随机分两组，各 10 道；同一 worker 配置、同一时段。
3. 实验组：人工/离线为每题写 1 条 FA（允许未验证），只在 exploit lane 注入这一条。
4. 对照组：原样。
5. 判据：解出率差值 + 首条打目标命令的比例 + 首个 flag 尝试出现时间。
6. 预注册写在 `experiments/fa-causal.yaml`，不改指标口径。

### 同期代码项（2026-11-18 复核后已修正）
- **上一版「扩展到全部 lane」的处方是错的，已撤销。** 复核 `coordinator.py:54` 的 `_RACE_LANES` 定义：共 **5 个 lane**（1 个 `exploit:known-path` + 3 个 recon + 1 个 `intel:public-poc`），`exploit:known-path` 是 **index 0，即第一个 worker**。门条件 `lane_key.startswith("exploit:")`（`:1914`）因此是**有意设计**，不是缺陷——把 FA 撒到 recon lane 反而会重复第一轮已验证失败的「全域侦察」。
- 真正的约束是 **FA 供给**，不是 lane 曝光：`first_action` 非空依赖配方命中或 CVE 解析（`known_exploit.py:1752 exploit_first_action`、`:2924 first_action_for_cve`）。ACTIVE 122 道仅 4 道有 FA（3%），说明绝大多数题**根本没产生 FA 字符串**。
- 因此代码侧该做的是**量化供给率**：对 ACTIVE 全量跑一遍 `exploit_first_action()` / `first_action_for_cve()`，统计「标题含 CVE 但没有对应条目」与「无 CVE 标题」各多少。这决定 P1 的语料缺口优先级，比改门条件更有信息量。
- 79 run（12%）无 race worker：确认是否应补（仍是待查项，但优先级低于供给率）。
- `_board_pointer()` 的 `has_first_action` 参数**已落地并接线**（`cli_solver.py:1999` 定义、`:2095` 传参、`:2272` 降级分支），此项已完成，不再列为待办。

### 验收
`exploit.first_action` 事件在实验组 10/10 出现；对照组 0/10；两组解出率差值有方向性结论（不要求显著，20 样本做不到显著，但要求效应量可读）。

### 现状问题

- 每 100 命令产 2.7 个 fact（已解 4.9）
- 观测信号 → 技法检索 macro 仅 22.4%，低于"全猜 rce"的 27.8%；deser/ssti/ssrf/xss 召回 0%
- 扩大 `box_names` / 更换索引键已验证无效

### 要引入的外部框架（只借结构，不整仓 fork）
| 项目 | 借什么 |
|---|---|
| EnIGMA | 交互式工具的状态机 + 命令级解析（对交互式 shell 类靶机） |
| PentestGPT | 任务树（PTT）作为唯一跨轮记忆，替代自由文本黑板 |
| D-CIPHER / VulnBot | planner-executor 分离，planner 不接触原始输出 |
| HackSynth | planner + summarizer 双角色，限制单角色上下文膨胀 |
| Cybench / InterCode-CTF | 评测口径与轨迹格式（便于与公开结果对比） |

### 固定流程（五段，每段有客观出口条件）
1. **资产枚举**：只允许确定性工具（端口/路径/指纹），幂等，结果进结构化表
2. **指纹匹配**：查表得产品/版本/CVE，纯确定性，不允许模型猜测
3. **假设生成**：模型产出 ≤N 条候选，每条必须写成"可用一条命令证伪的命题"
4. **廉价证伪**：一条命令一个假设，判定由输出解析给出（是/否/不可判定）
5. **利用**：只对判定为"是"的假设发载荷

关键：**"高准确率"不能靠模型自评**。1/2/4 三段是确定性代码，只有 3/5 用模型。要分段度量，否则无法声称准确率。

### 验收
在 30 道已标注题上，段 1+2 的指纹召回率 ≥90%、误报 ≤10%；段 4 的"不可判定"比例 <20%；整体"首次利用尝试前命令数"中位数从 5–6 降到 ≤3。

## P1：动态时间预算（对应"四"）

### 已完成的离线取证（2026-11-18，`scripts/analyze_truncation_points.py`）

数据源 `data/training/transitions-20261103T161417Z.jsonl`（282 Run / 43,850 transition），未解=166 UNSOLVED + 9 FAILED_ENGINE，已解=107 作对照：

| 指标 | 未解 (n=175) | 已解 (n=107) |
|---|---|---|
| 命令数中位 | **170** | **54** |
| 末 10 条有 fact 增量 | **84%** | 93% |
| 末 3 条含动手形态（带方法请求/载荷/脚本执行） | **62%** | 73% |
| 末 3 条全为浅层侦察 | 17% | 13% |
| 末窗 ≥50% 命令是此前重复过的 | **10%** | 7% |

四象限（未解）：`fact+ / exploit` 89、`fact+ / mixed` 32、`fact+ / recon` 26、`fact0 / exploit` 21、`fact0 / recon` **4**、`fact0 / mixed` 3。

**判读（与先前假设相反，必须修正）**：此前依据 `arena_solve.py:79` 的注释认为「未解题多数方向错误，加时间无用」。实测不支持该结论——**84% 的未解 Run 在被截断时仍在产出新 fact，62% 的最后 3 条命令已经是动手形态，真正「原地打转 + 只做侦察」的仅 4/175 = 2%**，命令重复率也只有 10%。「方向错误」不是主导失效模式。

**但这份数据不能直接证明「加时间就能解出」，两个混淆必须写明**：
1. **难度混淆**：未解组命令数中位 170 vs 已解 54，更难的题天然产生更多动作。它同时意味着「更活跃」和「更难」，无法区分。
2. **fact 通道不可信**：`delta_facts` 来自当前 fact 通道，全部 `verified=False`（fact 通道本身在待修清单里）。若 fact 是噪声，「仍在产出 fact」这一项的说服力随之下降。

**因此结论是「必须做重跑实验」而非「已经证明该加时间」**：1.5× 重跑是唯一能区分「截断」与「难度」的手段。

### 取证之后的动作（原计划不变）
**第一步（低成本）**：对 11-13 那 7 道失败的题，用固定 1.5×（2250 秒）重跑。鉴于上面 2% 的「方向错误」占比，**建议把重跑规模从 7 道扩到 12–15 道**（含 3–5 道已解题作正对照，检验「1.5× 不会把已解弄坏」）。两个晚上可得结论。

**第二步（仅当第一步有效）**：动态延长，规则必须客观：
- 延长触发：最近 5 分钟内新增可执行 fact ≥K，或最近 N 条命令把攻击面从"开放"收敛到"单一具体向量"
- 硬上限：2×（3000 秒），绝不无限
- 早停：连续 M 条命令无新增 fact 且无新死胡同 → 提前结束，把预算让给队列里下一题

风险：本队列是串行、每 agent 1 格环境，一次误延长直接吃掉下一题的时间。所以**必须先在离线回放上校准触发规则的精确率**，不能直接上线。

## P1：前端三块板（对应"十"）

### 已定位的真实根因（不是"感觉没显示完"）
| 现象 | 代码位置 | 原因 |
|---|---|---|
| 线索文字被切 | `frontend/src/styles/global.css:155` `.muteki-case-note-content { max-height: 68px; overflow: hidden; }` | 硬裁切，无展开入口；全屏也只有 82px |
| 来源行被省略号 | `global.css:157` `white-space: nowrap; text-overflow: ellipsis` | 证据引用永远看不全 |
| 线索被"摘要"顶掉 | `WorkspacePage.tsx:462` `text(semanticByCard.get(...)?.summary_zh, text(fact.summary_zh, ...))` | Codex 语义摘要覆盖原文，摘要天生更短 |
| 线索不全 | `WorkspacePage.tsx:447` 只取 `nativeState.key_conditions`，fallback 只取 `verified && evidenceCount>0` | 未验证但与案情相关的线索被结构性排除 |
| 任务状态看不出 agent 在做什么 | `run_events` 的 `worker_step` / `worker_command` 只在**发出线程有 running loop** 时落库 | 部分 lane 结构性空白，前端无数据可画 |

### 改法
- 卡片：`max-height` 改为折叠展开（保留摘要 + "展开原文"），`summary_zh` 作为副标题而非替换正文
- 来源/证据行改为可换行
- 看板新增「未验证线索」分区（灰显 + 标注 provenance），不再被过滤掉
- 任务状态板：每个 lane 一行 = 当前步 + 最后一条命令 + 输出摘要 + 已产 fact + 耗时/预算；"思考路线"用时间轴（假设→动作→结果）
  - **前置**：先修 `worker_step` 落库条件，否则这个板永远是空的
- 失败后「最有价值研究方向」：新增 `analysis.next_direction`，由三样东西确定性合成——最后 5 个 deadend、未验证假设、指纹匹配到但未尝试的漏洞类
  - 必须区分基础设施失败：余额不足 / 402 / 503 / 网络超时 / 代理失败 / 人为关机 → 标 `aborted_infra`，**不产出研究方向**，也不计入解出率分母

## P2：度量机制化（对应"八"）

不靠"多研判"，靠机制：
1. **可溯源性**：每个指标查询强制记录 code mtime / 数据窗口 / 过滤条件，落 `metrics_snapshot`
2. **代码是否真跑过**的自动断言：分析前检查 `max(run_events.created_at) > 代码 mtime`，不满足直接拒绝出数（`scripts/assert_feature_live.py`）
3. **选择偏差护栏**：任何对比同时打印 naive 率与匹配子集率，且必须打印两组样本量（FA 的 4/122 vs 127/142 就是必须自动暴露的那类）
4. **预注册**：实验假设与指标先写进 `experiments/*.yaml`，禁止事后挑选有利切分
5. **事件覆盖率看板**：每种事件类型的"应发生 vs 实际发生"计数，让"功能产 0 事件"立刻可见

## P3：自进化数据层 —— 改用 CyberEvolver（对应"七"，2026-11-18 重写）

### 为什么选它
- 仓库：`https://github.com/pursuingf/CyberEvolver`，论文 arXiv **2605.26195**，`IEEE S&P` 风格投稿，2026-05 公开，2026-10-26 最后推送。
- 核心主张：**进化的是 Agent Scaffold，不是模型权重**。失败轨迹被压缩、诊断，然后用来改写 prompt / 观测处理 / 技能库 / 接口规则，再跑下一代。
- 这恰好解开我们原来的死结：`fresh_reproduction_verified` 全库为 0 ⇒ 不能做权重微调。**Scaffold 进化不需要正样本，也不需要权重**。
- 公开结果（4 个基座模型平均）：NYU-CTF 25.7→**38.1**、AutoPenBench 44.7→**65.9**、CVEBench zero-day 16.9→**30.6**、one-day 30.6→**37.5**；平均比 seed 的 pass@16 高 **13.6%**，且**token 少 17.5%**。
- 关键对照设计：它不比"跑一次"，而是比 **seed 的 pass@16**——同样允许 16 次尝试，改 scaffold 是否比不变更有效。这是我们的实验一直缺的口径。

### 四层与我们现有结构的映射（这是接入的抓手）

| CyberEvolver 层 | 我们对应的东西 | 已知问题 |
|---|---|---|
| `LS` 策略（System Prompt） | `AGENTS.md` 头部 `RECON_DISCIPLINE` | 实测 9 种读法只有 6 种能读到头部 |
| `LI` 环境接口（shell 惯用法） | `container_exec` / `_containerize_environment` | 曾因反斜杠路径让整条事实通道死掉 |
| `LD` 领域知识（Skill / playbook） | `data/knowledge/playbooks/*.jsonl`（含 147 条 learned-boxes） | 只走 `box_names` 轴；ACTIVE 122 道仅 4 道有 FA |
| `LP` 感知（观测处理） | **fact 通道 + 观测压缩** | 每 100 命令 2.7 fact；49% 命令是浅层侦察 |

`LP` 是它最被低估的一层，也正好是我们最烂的一层：同一份 HTTP 响应几万字符，关键差异只有十几字符，原样塞进上下文就被忽略。

### ⚠ 必须先解决的合规问题（P3.0 的门槛）
GitHub API 返回 **`license: null`** —— 仓库**没有 LICENSE 文件**，按默认版权保留处理。因此：

| 做法 | 是否可行 |
|---|---|
| 直接 vendor / 拷贝其代码进本仓 | ❌ 不可，除非取得作者书面授权 |

### 三条硬约束（不遵守会重演"产出≠生效"）
1. **进度分只能用于同代兄弟排序，不能用于延长 deadline，也不能当能力指标。** 论文自己强调 80 分≠80% 成功率；它是模型判断，存在 reward hacking。这同时给"四、动态预算"划了边界：可以拿分数**选分支**，不能拿它**加时间**。
2. **串行队列 + 每 agent 1 格环境** ⇒ 16 次 rollout 不能真并发。进化必须在**离线回放**上做，只把最终变异体上线跑。
3. **论文与源码不一致**：论文说四层串行、后层可见前层修改；当前源码 `refiner_agent.py::generate_plan()` 走 `_execute_phases_parallel()` 并行。→ 固定 commit，并注明**以代码为准**。
